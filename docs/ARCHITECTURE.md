# Архитектура Qatrol Coin

Четыре процесса, один каталог, общение по HTTP на localhost. Общего состояния в памяти нет — только файлы на диске.

```
                 ┌──────────────────────────┐
   браузер  ───► │ server.js         :3000  │  статика + прокси
                 │  /api/*  → 3001          │
                 │  /pool/* → 3002          │
                 └───────┬──────────┬───────┘
                         │          │
                         ▼          ▼
              ┌──────────────┐  ┌──────────────┐
              │ miner.js     │  │ pool/server  │
              │ нода :3001   │◄─┤     :3002    │
              │ цепь, мемпул │  │ шары, выплаты│
              └──────┬───────┘  └──────┬───────┘
                     │                 │
                     ▼                 ▼
              blockchain.json     pool/miner-client.js
              wallets.json        (воркеры, SHA-256)
              sessions.json
```

## Нода (`miner.js`)

Держит цепь в памяти (`_dataCache`) и пишет её на диск с дебаунсом 500 мс. Читает `blockchain.json` один раз при старте. Майнит в свободном цикле: собирает шаблон из мемпула, добавляет REWARD и SYSTEM_FEE, перебирает nonce чанками по 3000, между чанками отдаёт event loop HTTP-запросам. Если пул активен, между чанками добавляется пауза.

Все данные — в `blockchain.json`:

```
{ chain: [block…], mempool: [tx…], wallets: { address: balance } }
```

Балансы не пересчитываются из цепи, а ведутся инкрементально в `applyBlock`. Поэтому любая запись блока — только через `applyBlock`, иначе балансы разъедутся с цепью.

## Блок

```
hash = sha256({ index, prevHash, timestamp, transactions, nonce, difficulty })
```

Порядок ключей важен: клиент пула собирает ту же строку вручную, чтобы не платить за `JSON.stringify` на каждый хэш. Валидный блок — хэш начинается с `difficulty` нулей.

Награда за блок — REWARD-транзакция из genesis-кошелька. Адрес genesis берётся из `chain[0]`, а не из `genesis.json`: файл может остаться от другого деплоя.

## Транзакция

Пользовательская транзакция подписана ECDSA P-256. Подписывается всё, кроме `signature`. Проверка: адрес восстанавливается из `publicKey`, подпись проверяется, у отправителя хватает баланса с учётом мемпула.

Комиссия 0.1%, минимум 0.0001. При применении блока комиссия списывается с отправителя и не достаётся никому; майнер получает её отдельной SYSTEM_FEE-транзакцией в том же блоке.

## Пул (`pool/server.js`)

Берёт у ноды шаблон через `/pool/template?miner=<адрес пула>`, раздаёт его воркерам и принимает шары с лёгкой сложностью 3. Когда шара проходит полную сложность блока — отправляет блок в ноду через `/pool/submit-block`. После принятого блока делит награду между активными воркерами пропорционально шарам, удерживает 2% и ставит выплаты в мемпул через `/pool/add-tx`.

Шары от предыдущего задания принимаются, пока есть текущее: воркер мог не успеть получить новое.

## Авторизация (`auth.js`)

Приватный ключ хранится зашифрованным: AES-256-GCM, ключ из пароля через PBKDF2-SHA256, 100 000 итераций, случайные соль и IV. Сессия — 32 случайных байта, живёт 7 дней, передаётся заголовком `X-Session-Token` или cookie. Один кошелёк — одна активная сессия.

## P2P (`p2p/node.js`)

Раз в 10 секунд нода опрашивает пиров: сверяет высоту цепи, тянет `/chain/p2p`, проверяет блоки и заменяет цепь, если у пира длиннее и валиднее. Новые блоки анонсируются через `/block/push`. Список пиров — `peers.json`, начальные адреса — `QTR_BOOTSTRAP_PEERS`.

## Что легко сломать

- Записать блок в цепь мимо `applyBlock` — балансы разойдутся.
- Менять ключи или порядок полей в блоке — все старые хэши станут невалидными.
- Запускать ноду и пул на одном каталоге с разными версиями кода — пул перезапишет `blockchain.json` своими выплатами поверх чужой копии.
- Держать `QTR_MINER_PRIVATE_KEY` в репозитории — ключ утечёт в первый же публичный пуш.
